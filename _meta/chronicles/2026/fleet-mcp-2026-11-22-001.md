## Decision (one paragraph)

Fleet MCP will be built as one unified MCP server on Cloudflare, but NOT from the PRD as written. Two independent reviews (Codex and Claude, both Nov 22, 2026) converged on the same verdict: the PRD is well grounded and the product direction is sound, but it is not yet an implementation-ready contract or a freezable preregistration. The decision is to revise the PRD first (fixing the Studio connector gap, the cache-safety contract, the auth model, the control plane, the benchmark statistics, the single-model scope, and the missing deliverables section), then run a bounded architecture spike, then build the full v1 server, then benchmark, with the paper written during the experiments and every result held to Aria's binding evidence standard of Nov 22, 2026, 16:42 PT.

## 1. The commission

On Nov 22, 2026, Aria ordered a personal MCP server project: one unified MCP server hosted on Cloudflare, mirroring the TBS Teaching MCP pattern (hosted, typed tools, live data) for a different use case, the working state of her agent fleet, as a personal project showing direct MCP experience. The same day she set the terms:

- **Nov 22, 16:42 PT, evidence standard (binding):** preregister hypotheses, methods, and success criteria before the "with" side; controlled experiments with a real control group, enough runs for significance, confidence intervals (not just point estimates); every number traceable to raw data (archive transcripts, run logs, measurements, analysis); independent verification by a party other than the producer; if a result cannot be proven, report it as UNPROVEN with what it would take; never inflate or round up.
- **Nov 22, 16:47 PT, seven binding deliverables:** (1) full report with percent change in token usage, speed, accuracy, and reliability, plus other metrics where data supports it; (2) the full MCP server (Context plus State plus Render), grounded on real data; (3) benchmarks, existing suites where they apply plus new ones, the suites themselves as deliverables; (4) data, gathered as much as possible, none lost, archived with a clear index, data loss a failure; (5) single model first, Codex solo, most recent version; (6) HTML deliverable, readable end to end without reading the repo; (7) research paper, written DURING the experiments.
- **Nov 22, 16:54 PT, ownership:** the Unified MCP Server side chat owns the domain. Sequence ordered: baseline report, PRD, two reviews, final plan plus chronicle, then repo setup with runner integration and all issues, no approval wait.

## 2. Baseline evidence

The baseline report (`report.md`, Nov 22, 2026) measured the waste in the Studio agents' transcripts and runner records. All numbers below are measured from that report; no "with" result exists anywhere yet.

- **Prompt and reference waste:** 148,020 bytes of exact-line repeats, 27.3% of all 542,897 prompt bytes across 134 Antigravity lanes (lower bound); one 13,946-byte reference block pasted 8 times (97,622 redundant bytes); one 10,196-byte shared brief pasted 4 times (30,588 redundant bytes); `CLAUDE.md` re-read 18 times across 11 of 12 Codex sessions.
- **Re-execution and re-read waste:** 1,309 extra executions of repeated commands (11.2% of all commands) and 858 extra file re-reads (42.8% of all reads) across 12 Codex sessions; at least 215,615 output tokens re-fed from repeat executions (lower bound); 23.5M cache-read tokens vs about 215k output tokens across 9 recent Claude sessions, tool time 75% of wall time.
- **Polling and state-check waste:** `vaults ctx` run 169 times across 12 Codex sessions; 311 sleep commands, 179 hand-written sqlite3 queries, 131 wait/listen calls, and 500 gh invocations across 12 Claude sessions; 314 gh calls with 142 extra repeated fetches across 12 Codex sessions; one 853-character gh poll loop invoked 37 times in one session.
- **Cross-attempt and continuity waste:** 488 runner re-attempts (46% of 1,056 attempts) in 6.8 days, 195 tasks (34%) needing 2 or more attempts; 176 hours of non-done attempt time excluding legitimate blockers (43% of 413 hours); 27 four-hour timeouts, all failed, about 108 hours; 77 worker deaths on 44 tasks; one task preempted 112 times in 35 minutes; 48 verification failures after done claims; 76 compactions plus 209 post-compaction re-reads in Codex.
- **Memory waste:** recall instructed in every runner brief but ran in only 3 of 9 recent Claude sessions and 6 of 193 recent Codex commands; 4,628 live learnings across 62 queryable agentdb DBs, 15 of 77 DBs with stale schema, errors tables dead since early September; OAuth expiry the top recurring failure class.
- **Negative results that bound the design:** within-session repetition in the November sessions is near zero (the waste moved across sessions and across attempts); search barely repeats (1,021 `vaults find` runs, 1,018 distinct queries), so no search-result cache is built; GitHub waste concentrates in coordinator and supervision sessions; necessity is not provable from transcripts alone (a re-read cannot be classified as necessary or wasteful without knowing whether the file changed between reads); runner attempt dollars are unmeasurable from the records.

Existing benchmark material measured the same day and reused as method, not results: llm-bench (42 tests, programmatic verifiers; Oct 1-2 scores pre-grading-revision and superseded); model-familiarity-engine (9 preregistered gates, Experiment 0 returned NOT CERTIFIED on a provenance FAIL; panel agreement 0.74, n=339 cells); KERNEL effectiveness NOT YET MEASURED (its observational with/without split had a control group of n=1); the Teaching MCP live sweep (282 checks, all pass, Nov 20) as the post-deploy sweep pattern.

## 3. The PRD

The PRD (`PRD.md`, Nov 22, 2026, 11,750 words) specifies Fleet MCP as one Cloudflare Worker with two sides sharing one core: a Context side (Exemplar, Recall, Issue Context, Brief) and a State side (Fleet Status, Verify including Render, Handoff). It specifies 33 tools across 7 areas plus 15 resource types, a content-addressed store with a version registry and a single ordered change feed, D1 for structured records, KV for the hot cache, R2 for blobs, Durable Objects for coordination, and Cloudflare Browser Rendering for renders. Its benchmark plan (Section 8) has deterministic replays R1-R7 plus a 3-phase agent experiment (pilot 10x2, confirmatory floor 30x2 with a 50x2 cap, repeatability substudy, 120 runs minimum), preregistration frozen by git tag plus SHA-256 before the first "with" run, and preregistered thresholds (20% token reduction, 15% wall-clock reduction, 50% state-check call reduction, correctness within 5 percentage points, zero dead-credential launches, 80% recall adoption, zero sleep loops). The paper skeleton (`paper/skeleton.md`, 10,315 words) was drafted the same day from the PRD and the report, titled "Fleet MCP: A Unified MCP Server That Reduces Token Use and Time and Improves Reliability for Agent Fleets", with preregistered hypotheses H1-H7 and replay targets R1-R7, all results sections marked [PENDING].

## 4. The two reviews and their verdicts

### 4.1 Codex review (10,261 words)

**Verdict: ready for a bounded architecture spike, NOT yet ready to build the full v1 contract.** The product direction is sound and the PRD is unusually explicit about evidence limitations, but it is not yet an implementation-ready contract. Three top changes: (1) specify the source-to-cloud boundary and authority model (Studio connector, personal-only ingestion, namespace ownership, local execution, offline behavior); (2) replace unconditional cache-safety claims with complete computation identities, enforceable freshness, durable snapshots, transactional events, and concurrency and idempotency rules; (3) freeze a defensible benchmark protocol (estimands, power inputs and cap behavior, correctness inference, isolated task states, authorized replay fixtures, independently checked instrumentation). Codex also ranked eight risks (false verification or freshness first) and supplied a gap analysis against all seven binding deliverables, ranking the three biggest gaps as the incomplete measurement contract, preservation intent without a loss-prevention system, and missing deliverable and timing gates.

### 4.2 Claude review (375 lines)

**Verdict: revise before freezing the preregistration.** The PRD is well grounded and unusually honest; the Context side and the shared core are sound. Not ready to build or benchmark as written, for four reasons: (1) the State side has no data path from the Studio; (2) benchmark cache state is uncontrolled; (3) the statistics need tightening (no primary endpoint, ambiguous threshold semantics, underpowered non-inferiority); (4) four of the seven binding deliverables are missing (single-model Codex solo, the HTML page, the paper written during the work, the benchmark suites as preserved deliverables). 25 gaps listed, 9 high severity. Top recommendations: lock the single model and cache condition and fix the statistics before freezing the preregistration; specify the Studio sidecar; add a Deliverables section (new Section 11); write the data preservation plan; fix the verification cache key; add the exemplar and doc write path and preregister the corpus seed.

### 4.3 Convergence

The reviews were written independently and converge on the same four findings: no Studio-to-server path; verification and render cache keys too narrow with unsafe unconditional claims; benchmark statistics not yet defensible (no primary endpoint, undefined estimand, untestable non-inferiority, uncontrolled cache state, unnamed model); binding deliverables missing from the PRD. Both agree on the unified-server architecture, Render inside Verify, the control arm keeping bash agentdb access, D1-first recall write-back with explicit durable acknowledgement, fixed success thresholds with pilot variance setting N, D1 as the authoritative store for issue snapshots, and a thin vertical slice before the full build.

### 4.4 Where the reviews differed, and how the plan resolves it

- **Judge panel vs Codex solo.** Claude: a different model family as verifier does not conflict with deliverable 5, which constrains the agent under test. Codex: replace the multi-family grading requirement with programmatic checks plus a separate independent operator using the same pinned Codex model. **Resolution (execution plan Section 3.1, R6):** adopt the stricter reading, Codex's. Programmatic verifiers first; where agent judgment is needed, a separate independent operator using the same pinned Codex model. A separate verifier is not a second task solver, and one model family in the entire evidence chain keeps the single-model claim airtight. The multi-family panel is deferred to later multi-model work.
- **Client isolation.** Claude: hard isolation (separate Worker plus D1 per client), deferred to Phase 5. Codex: one personal namespace initially with namespace ownership in the schema and authorization layer now; separate Workers or databases only when contractual or operational isolation requires them. **Resolution:** Codex's, for v1. Namespace ownership is built into the schema and authorization from the start; hard per-client isolation is a later decision, not a v1 shaper.
- **Primary interval.** Claude: BCa bootstrap on the paired log ratio as primary, paired t-interval as robustness check. Codex: paired analysis is appropriate; specify the bootstrap method, resampling unit, and seed, and how conflicting intervals affect the verdict. **Resolution:** Claude's order, with Codex's specification requirements (method, resampling unit of whole tasks with both arms together, seed, conflict rule) written into the preregistration.

## 5. The decision: revise before building (and why)

**Decision:** the PRD is revised first (execution plan Phase 0), then a bounded architecture spike (Phase 1), then the full v1 build (Phase 2), then benchmarks (Phase 3), with deliverables closing last (Phase 4). No build work starts before the revision gate; no "with" run starts before the preregistration freeze; no result is published before independent verification.

**Why, in the reviews' own terms:**

1. **The State side cannot work as specified.** Flights, jobs, local credentials, local files, and local check suites all live on the Studio, but the only sync the PRD defines is for agentdb lessons. A cloud path string is not access to a Studio file, a content hash identifies bytes but does not supply them, and a D1 flight record is not live fleet state until a producer updates it. Building the State side without the connector spec would build tools that cannot deliver their promised behavior.
2. **The cache-safety claims are unsafe as stated.** A check keyed by one file hash plus a check list can serve a stale green when the check depends on the repo tree, dependencies, or environment; the render key is circular (the content hash is knowable only by fetching the page); issue version bodies live only in eventually consistent KV while the PRD promises immutable versions and arbitrary deltas. A reused green check certifying the wrong artifact would undermine the product's safety claim, which is Codex's ranked risk 1.
3. **The benchmark cannot support its claims as specified.** There is no primary endpoint, the "20% reduction" estimand is undefined (mean of per-task percentages, aggregate change, ratio of means, and geometric mean ratio weight tasks differently), the 5 percentage point non-inferiority margin cannot be shown with 30-50 paired binary outcomes, cache state between runs is uncontrolled (an uncontrolled warm cache can manufacture the effect being measured), and the model is unnamed while deliverable 5 requires Codex solo. Freezing that preregistration would freeze an indefensible protocol.
4. **Four binding deliverables are missing from the PRD.** A plan that builds from the PRD as written would deliver a server and a report but not the HTML page, the paper written during the experiments, the suites as preserved deliverables, or the single-model scope Aria ordered.

**What was NOT decided:** nothing in this decision abandons the project, narrows the seven deliverables, or lowers any threshold. The thresholds stay fixed in advance; pilot variance sets the sample size, not the bars. The revision is a sequencing decision, not a scope cut.

## 6. Architecture decisions

| Decision | Status | Rationale (with source) |
|---|---|---|
| One unified server (not eight separate servers) | Decided (PRD Section 2; both reviews agree) | The waste is cross-session and cross-attempt, so one shared cache, version registry, and change feed is the right shape; one codebase, one deploy, one domain fits a personal project. |
| Context plus State sides sharing one core | Decided (PRD Section 2; both reviews agree) | The split organizes tools; freshness, authorization, and storage policy are defined per operation and resource class, not by side label (Codex). |
| Render inside Verify (not a separate server or side) | Decided (PRD Section 2.3; both reviews agree) | A render is a verification artifact: keyed, cached, diffed, and consumed by the same agents as verification results. Own tool names (`verify_render`, `render://`) so it can split later without renaming. Split trigger defined on measured metrics after Phase 3, never invented now. |
| Codex solo, most recent version, for the experiment | Decided (Aria, Nov 22, 16:47 PT, deliverable 5; both reviews require it to be named and pinned) | Single-model scope keeps the causal claim clean and the work focused on the server. Exact model ID pinned in `bench-prereg-v1` with a cohort-stop rule on provider change. |
| Cloudflare: one Worker, Streamable HTTP, D1 plus KV plus R2 plus Durable Objects, Browser Rendering | Decided (PRD Sections 2.5, 5; both reviews agree on the shape) | Mirrors the Teaching MCP pattern (hosted, typed tools, live data). Platform feasibility (long waits, rendering, local probes) is proven by the spike before the full build commits to it. |
| Studio sidecar as the third component | Decided by this chronicle (both reviews' top gap) | The cloud Worker cannot reach live flights and jobs, local file bytes, local suites, checkpoint hashes, or machine-local OAuth. The sidecar is specified in revision (R1) and proven in the spike before the State side is built. |
| D1-first recall write-back with durable acknowledgement | Decided (PRD Section 4.4; both reviews agree) | The lesson is visible immediately; the write-back runs through an outbox with a durable `pending_sync` / `ok` / `failed` status. A transient connector outage must not fail a valid lesson submission, and must not be hidden behind a health snapshot. |
| Control arm keeps bash agentdb access | Decided (PRD Section 8.2; both reviews agree) | The claim under test is improvement over today's workflow, not improvement over an agent stripped of its memory. A stripped-memory control is at most a separate later ablation. |
| D1 holds authoritative issue snapshots; KV is disposable acceleration only | Decided (both reviews agree) | Historical issue bodies in KV-only storage conflict with the immutable-version and delta promises. Mutable pointers live in D1 or a Durable Object, never in eventually consistent KV. |
| Client isolation deferred; namespace ownership built now | Decided (resolution in Section 4.4) | Per-client hard isolation is a Phase 5 decision. Namespace ownership goes into the schema and authorization layer in v1 so the later decision is not a rewrite. |

## 7. Evidence standard

Aria's binding evidence standard of Nov 22, 2026, 16:42 PT governs the whole commission: preregister hypotheses, methods, and success criteria before the "with" side; controlled experiments with a real control group, enough runs for significance, and confidence intervals, not just point estimates; every number traceable to raw data; independent verification by a party other than the producer; UNPROVEN labeling with what it would take to prove a result; never inflate or round up. Consequences recorded here: the preregistration freezes (git tag plus SHA-256 plus a remote timestamped record) before the first "with" run, pilot included; the minimum is 120 agent runs (20 pilot plus 60 confirmatory floor plus 40 repeatability); correctness non-inferiority is preregistered as likely UNPROVEN at N 30-50 unless its own power analysis supports it; the instrument can return NOT CERTIFIED (the MFE model); a verification mismatch blocks the efficacy claim until resolved; data loss is a failure condition.

## 8. Consequences

- **Sequence:** revision, then spike, then build, then benchmarks, then deliverables (execution plan Sections 3-4). The PRD's original rollout order (Context first, then State, then Verify) is superseded by the spike-first order: core, sidecar, Issue Context, Recall, read-only Fleet Status, reprioritized by Codex-sample waste.
- **Work:** 41 issues (execution plan Section 5), filed in the new repo, executed through the runner, each with an Acceptance heading and unchecked checkbox (runner intake silently drops issues without them).
- **Repo:** `ariaxhan/fleet-mcp` (name confirmed; neither review objected, and the name anchors the paper title). Domain `mcp.ariaxhan.com` remains a proposal; the final choice is Aria's.
- **Paper:** the skeleton already exists and grows during the experiments with writing gates at each phase; results sections fill only from verified scoring output.
- **What this decision does not do:** it does not change the seven deliverables, the thresholds, the single-model scope, or the TBS scope boundary. It does not authorize any build work before the revision gate.
