What was built, and why

A baseline study of the fleet's own transcripts and runner records (baseline report) measured where agents waste work. Across 134 Antigravity lanes, 27.3% of prompt bytes were exact-line repeats. Across 12 Codex sessions, 11.2% of shell commands were repeat executions and 42.8% of file reads were re-reads. Across 12 Claude sessions, agents ran 311 sleep commands in polling loops and 500 GitHub CLI calls. In 6.8 days of runner records, 46% of attempts (488 of 1,056) were re-attempts (all figures: baseline report Part 1).

Fleet MCP is the response: one server that gives agents structured, cached, versioned access to fleet state, so they stop re-reading, re-fetching, re-polling, and rebuilding context after restarts. The PRD specifies 33 tools across 7 areas. Build status: not started. Building waits on gate G0 (PRD v2 addressing both reviews) and a platform spike (gate G1).

Scope: a personal project with its own corpus, enforced by a repo allowlist in code. It never reads, serves, or benchmarks TBS data, repos, issues, or MCP content.

Architecture

Context side (what the agent needs to know): reference exemplars, agentdb recall, GitHub issue state, and briefs, served as versioned resources with diffs. State side (what is true now): job and flight status with credential preflight, cached verification and renders, and handoff checkpoints, served as live services that wait server-side instead of in sleep loops. Both sit on one core: a content-addressed store keyed by SHA-256, an append-only version registry, one ordered change feed, and a cache that labels every response hit, miss, stale, or bypass. A Studio-side connector pushes local flight state and probe results in; credentials never leave the machine (execution plan item R1).

Methods

  • Design: paired controlled experiment on Codex solo, one pinned model ID. Control arm works as agents do today (brief, files, CLI, bash agentdb). Treatment arm adds Fleet MCP. Arm order randomized, fresh agents and isolated worktrees per arm, caches reset cold per run.
  • Runs: pilot 10 tasks x 2 arms (not pooled), confirmatory floor 30 x 2 up to a cap of 50 x 2 powered from the pilot SD upper confidence limit, repeatability substudy 10 tasks re-run twice more per arm. Minimum 120 runs.
  • Primary endpoint: total tokens per task (input, output, cache-read reported separately), estimated as the mean per-task log ratio back-transformed to percent change, BCa bootstrap 95% CI primary, paired t-interval as robustness check. Wall clock and correctness are key secondaries under Holm correction; everything else is exploratory.
  • Deterministic replays of the measured baselines run first and report exact counts (targets R1 to R7).
  • Failures, timeouts, and aborted runs are outcomes, not exclusions. Intent-to-treat: an agent that ignores the tools still counts.

Full protocol: execution plan (Section 3.4), paper Section 5.

UNPROVEN items

A result that cannot be proven to the evidence standard is labeled UNPROVEN with what it would take to prove it. Known in advance:

  • H4: UNPROVEN (expected): a 5 point margin cannot be shown with 30 to 50 paired binary outcomes; proving it needs a powered sample computed from the pilot
  • Avoidability of baseline repetition: transcripts count repetition exactly, but cannot show a re-read was unnecessary without knowing whether the file changed. Bounded, not proven (baseline report, Limitations).
  • Zero-event criteria (H5, H7): zero observed events will be reported with a finite-sample interval, never as proof of a zero rate.

Limitations

  • Single model (Codex, one pinned version): results do not transfer to other models without a separate run.
  • One fleet's tasks: personal-project jobs only, preregistered selection rule, selection bias is a named risk.
  • Baseline sample: the Codex sample is the 12 largest of 936 rollouts (1.3% of files); its rates describe large sessions.
  • The server's own schema and tool-response tokens count against it; the benchmark measures net effect.
  • Correctness non-inferiority is likely underpowered (see H4).
  • Cache staleness and stored-content prompt injection are design risks with mitigations, not eliminated risks.
